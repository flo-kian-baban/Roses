## 1. Stack and architecture

Two phases. The MVP runs from Kian's machine and a free preview; the move to hosted services happens only after the owner has seen the MVP. Nothing before that depends on a paid plan, a hosting account beyond a free Vercel account for the preview, or a domain.

| Choice | Decision | Why | Trade-off |
| --- | --- | --- | --- |
| Framework | Next.js (App Router), TypeScript. Public pages, admin UI and admin API in one project | Kian's stack; one codebase; static rendering built in | The preview build must switch the admin off (see "MVP preview") |
| Database (MVP) | Postgres 16 in Docker on Kian's machine (`docker compose up -d`), schema in plain SQL migration files (`db/migrations/001_init.sql`, …) applied by `npm run db:migrate`; queries through the `pg` driver; input validated with `zod` in server actions | Kian's decision; standard Postgres only, so the move is a connection-string change | No ORM: queries are hand-written SQL (about 20 of them); migrations are plain files |
| Database (after the MVP) | Supabase Postgres, same migrations, same SQL; `DATABASE_URL` changes | Kian's decision | Supabase's connection pooler needs the session mode for migrations; rehearsed before the switch |
| Standard-features rule | Tables, JSONB, `numeric`, `timestamptz`, `gen_random_uuid()`, CHECK constraints, indexes, views. No extensions, no Supabase-only features, no triggers | Portability | Some validation lives in the app instead of the database |
| Public pages | One static page per venue (`/senso`, `/kebab-land`), both languages embedded. Built from the database at build time (`force-static`). MVP: built on Kian's machine and uploaded. After the move: same build on Vercel plus on-demand revalidation when an admin saves | No database query per visit; fast LCP; works on a free plan | MVP previews are rebuilt by hand after edits (1–3 minutes); live revalidation only after the move |
| Admin | Same Next.js project under `/admin`, server actions for every mutation. MVP: runs locally (`npm run dev`) against the local database; `/admin` returns 404 in preview builds (`PREVIEW_BUILD=1`). After the move: deployed with the public pages | Kian's decision; nothing of the admin reaches the preview | During the MVP edits happen only on Kian's machine |
| Images | MVP: `<img>` tags pointing at the client's own photo URLs with explicit width/height, Next.js image optimization off. After the move: photos copied to our own storage (decided at the move; Supabase Storage is the obvious candidate) | Kian's decision: download nothing for the MVP | Source hosts control availability; Mealsy URLs carry upload timestamps and may change |
| Auth | Admin accounts (owner, Kian): email + password, argon2id. Staff: 6-digit PIN per person, argon2id, venue-scoped, revocable. Signed HttpOnly cookie sessions (`jose`). Lockout: 5 failures lock the venue + IP pair for 15 minutes; 50 failures per hour per venue lock the venue and raise an alert shown in the admin until email exists | Adopted decisions | PINs are weak secrets; hashing and lockout make them acceptable |
| Persian | Client-side toggle flipping `lang` and `dir` on `<html>`; both languages in the static HTML; Vazirmatn font; Western digits for prices | Rulings 6; adopted | About 40 KB more HTML per venue |
| Logo animation | Inline SVG + CSS, shown at once, removed when the menu has painted (cap 1.5 s); skipped when `localStorage` says the venue was seen or `prefers-reduced-motion` is set | Build decision | Must look right when cut short |
| Branding | No "Mealsy" and no "Flo" anywhere visible: UI text, titles, metadata, alt text, error pages, console output shipped to the browser. No "built by" credit. Source labels only in `source` columns and import files. MVP exception: photo URLs point at the client's own hosts | Kian's decision | A grep over the built output is part of every acceptance check |
| Styling | Tailwind CSS with per-venue theme tokens read from the venue row | Fast phone-first layouts | Utility classes in markup |
| Verification | Playwright (reusing `tools/capture`) against the preview URL with the bypass header; Lighthouse CLI with `--extra-headers` for the bypass; psql for database checks | Verification standard | Lighthouse varies; three runs per check |

### Edit to public

- MVP: admin save → local Postgres → revision row → `npm run preview:deploy` (`vercel build` reads the local database and prerenders both venue pages; `vercel deploy --prebuilt --prod` uploads `.vercel/output`). The owner sees the change on the next open of the preview link, typically 1–3 minutes after the command.
- After the move: admin save → Supabase → revision row → `revalidatePath('/<venue>')` → the next request re-renders the page once and the CDN caches it; visible within seconds. A 10-minute time-based revalidation is the safety net, and the admin has a "Republish" button.

## 2. Data model (Postgres)

Bilingual text is JSONB `{"en": "…", "fa": null}`; `fa` null means fall back to English. Money is `numeric(8,2)` in CAD; null means no price known. Nested parts (bilingual text, variants, add-ons, combo components, photo, notes, source refs) are JSONB columns; everything relational (venue, section membership, history, users) is a table.

```sql
create table venues (
  id          text primary key,                 -- 'senso' | 'kebab-land'
  name        jsonb not null,                   -- {"en": "Senso Café & Bites", "fa": "…"}
  locations   jsonb not null default '[]',      -- [{"label": {"en": "Dine-in", "fa": null}, "address": "9218 Yonge St …", "phone": null}, …]
  brand       jsonb not null default '{}',      -- {"logo": null, "colors": {}, "fonts": {}}
  settings    jsonb not null default '{"showPersianDrafts": true}',
  updated_at  timestamptz not null default now()
);

create table sections (
  id          uuid primary key default gen_random_uuid(),
  venue_id    text not null references venues(id),
  name        jsonb not null,
  note        jsonb not null default '{"en": null, "fa": null}',
  position    integer not null,
  listed      boolean not null default true,    -- Kian: admins list/unlist any section
  fa_draft    text[] not null default '{}',     -- fields whose Persian is a machine draft
  source      jsonb not null default '[]',      -- internal only, never rendered
  updated_at  timestamptz not null default now()
);

create table items (
  id          uuid primary key default gen_random_uuid(),
  venue_id    text not null references venues(id),
  name        jsonb not null,
  description jsonb not null default '{"en": null, "fa": null}',
  price       numeric(8,2),                     -- null = needs price
  variants    jsonb not null default '[]',      -- [{"label": {"en": "6 oz", "fa": null}, "price": 9.00}, …]
  add_ons     jsonb not null default '[]',      -- [{"label": {"en": "Lactose Free", "fa": null}, "price": 4.00}, …]
  components  jsonb not null default '[]',      -- [{"item_id": "…", "label": {"en": "Barg Kebab", "fa": null}, "qty": 1}, …]
  serves      text,                             -- "2", "3-4"
  photo       jsonb,                            -- {"url": "…", "width": 1024, "height": 998, "alt": {"en": "…", "fa": null}}
  notes       jsonb not null default '{"allergens": [], "dietary": [], "halal": null, "text": {"en": null, "fa": null}}',
  listed      boolean not null default false,
  fa_draft    text[] not null default '{}',
  source      jsonb not null default '[]',
  updated_at  timestamptz not null default now(),
  updated_by  jsonb,                            -- {"kind": "admin" | "pin", "id": "…", "name": "…"}
  constraint listed_requires_price check (not listed or price is not null or jsonb_array_length(variants) > 0)
);

create table item_sections (                    -- an item shown in more than one section
  item_id     uuid not null references items(id) on delete cascade,
  section_id  uuid not null references sections(id) on delete cascade,
  position    integer not null,
  primary key (item_id, section_id)
);

create table revisions (                        -- edit history with one-click restore
  id          bigserial primary key,
  venue_id    text not null,
  table_name  text not null,                    -- 'items' | 'sections' | 'venues'
  row_id      text not null,
  action      text not null,                    -- create | update | delete | restore | list | unlist
  before      jsonb,
  after       jsonb,
  by          jsonb not null,
  at          timestamptz not null default now()
);

create table admins (
  id            uuid primary key default gen_random_uuid(),
  email         text not null unique,
  password_hash text not null,                  -- argon2id
  name          text not null,
  created_at    timestamptz not null default now()
);

create table pins (
  id           uuid primary key default gen_random_uuid(),
  name         text not null,                   -- the person
  role         text not null check (role in ('owner', 'staff')),
  venue_ids    text[] not null,
  pin_hash     text not null,                   -- argon2id; the PIN is shown once at creation
  created_by   uuid references admins(id),
  created_at   timestamptz not null default now(),
  revoked_at   timestamptz,
  last_used_at timestamptz
);

create table login_failures (                   -- lockout counters
  key               text primary key,           -- '<venue>:<client address>' and 'venue:<venue>'
  failures          integer not null default 0,
  window_started_at timestamptz not null default now(),
  locked_until      timestamptz
);

create table admin_alerts (                     -- shown in the admin until email exists
  id         bigserial primary key,
  venue_id   text,
  kind       text not null,                     -- 'lockout-cap'
  message    text not null,
  created_at timestamptz not null default now(),
  seen_at    timestamptz
);

create view items_needing_price as
  select i.* from items i
  where i.price is null
    and (jsonb_array_length(i.variants) = 0
         or exists (select 1 from jsonb_array_elements(i.variants) v where (v->>'price') is null));

create index on items (venue_id, listed);
create index on item_sections (section_id, position);
create index on revisions (venue_id, at desc);
create index on revisions (table_name, row_id, at desc);
create index on pins using gin (venue_ids);
create index on login_failures (locked_until);
```

Listing rules (Kian and the PM):

- `listed` on items and sections is the only visibility switch. Listed = shown to customers; unlisted = admin only. There is no "hidden" state.
- An item can be listed only if it has a price, or, when it has sizes, every size has a price. The CHECK constraint enforces the simple half; the server action enforces the per-size half (a subquery is not allowed in a CHECK) and reports "needs price".
- A section shows to customers only if it is listed and has at least one listed item. This is a query rule at build time, not a stored flag.
- `items_needing_price` drives the "needs price" badge and list in the admin.

How the captured shapes map:

| Captured shape | Example | Column |
| --- | --- | --- |
| Size variants | Red Wine Sangria 13 oz $15 / 26 oz $30; Ketel One 1-shot $7 / Bottle $120; Pinot Grigio 6 oz $9 / 9 oz $13 (16 bar items) | `variants`, `price` null |
| "Serves N" | Platter 3 $150.99, "Serves 3-4" (7 items) | `serves` |
| Combos built from other items | Soltani, Mohtasham, Platters 1–6, Kaseh Kebab, Mixed Appetizer Platter (20 items) | `components`; `item_id` set when the name matches an item of the same venue, otherwise label only |
| Add-ons | Senso coffee milk choice (Lactose Free +$4, others $0), salad "Add Atlantic Salmon +$9", ice cream flavour choice (7 Senso items carry modifier groups) | `add_ons` |
| Item in more than one section | Halim (Persian Breakfast and Appetizer on Mealsy) | two rows in `item_sections` |
| Bilingual text | "Pomegranate majoun معجون انار"; section "Fresh Juice آبمیوه طبیعی" | split into `en` / `fa` at import |
| Photos | Mealsy photo URL per Senso item; website dish photos for Kebab Land | `photo` with the source URL (MVP) |
| Allergen / dietary / halal | nothing in any source | `notes`, empty, editable by owner PINs and admins only |
| Unpriced content | 147 Senso website-only names | `listed = false`, `price` null, appears in `items_needing_price` |

## 3. Import plan (one source per venue, no merging across sources)

The import is `tools/import/`: it reads `data/raw/<source>/2026-10-07/`, writes `data/import/<date>/<venue>/{venue}.json` (the rows) and `import-report.md`, and loads the rows with `npm run import -- <venue>`. Loading is idempotent (upsert on `source` refs). The import never writes allergen, dietary or halal fields.

| Venue | Source | Mapping |
| --- | --- | --- |
| Senso | Mealsy "Senso Café Menu" (file `decoded/…datacategory-1….decoded.json`, menu by name) | 15 `MenuSections` → sections, listed, in `Position` order; 148 `MenuItems` → items, listed, `Price`, `PhotoPathOnline.En` → `photo.url`, `Description.En` → description; `ModifierGroups` → `add_ons`; Persian split out of names, descriptions and section names. The "Third-Party Menu" in the same payload is ignored |
| Senso | sensocafe.ca (the manifest's widget extraction and `html/index.html`) | Only two uses: (1) a website description is copied to a Mealsy item only when that item's Mealsy description is empty and the names match exactly after normalisation (at most 23 candidates; the exact count is in the report); (2) the 147 website-only names become unlisted items with `price` null under their website section names |
| Kebab Land | roseskebablands.com/menu-land | Heading → section (7, including Dessert); "Name $price" widget → listed item; following widgets → description; "Serves N" → `serves`; descriptions naming other dishes → `components`; dish photos → `photo.url` |
| Kebab Land | roseskebablands.com/drinks | Heading → section (11); "6 oz $9 9 oz $13"-style line → `variants`; "Classics" has no items and only the note "A sip of the classics", so it never shows |
| Kebab Land | Mealsy | not used |

Website section names for Senso website-only items: the website heading is used as the section name. Where a Mealsy section already has that name ignoring case and a plural "s" (Appetizers → Appetizer, Salads → Salad, Senso Pizzas → Senso pizza, and the exact matches Senso Signature, Persian Breakfast, Main Course, Ice Cream, Milkshake, Dessert), the item is placed in the existing section; otherwise a new section with the website name is created (Hot & Cold Beverages, Pancake & Waffle, Juice Bar). Juice sub-block lines go under Juice Bar. New sections contain only unlisted items, so they do not show until something in them is priced and listed (Open question 2).

Listed or unlisted at import: every item with a price is listed; every item without a price is unlisted and appears as "needs price". Items with sizes are listed only when every size has a price (all 16 bar items qualify). Sections are listed; whether they show follows the listed-item rule.

Venue rows: Kebab Land stores both addresses (9218 dine-in, 9108 take-out) in `locations`; phone numbers are left empty because the website's displayed number and its call links disagree, and the owner enters the right one in the admin. Senso stores 9218.

Branding at import: `source` holds the capture slug and the source id; no venue-visible text contains "Mealsy" or "Flo" (the import checks every `name`, `description` and `note` value and fails if either string appears). Photo URLs may point at the client's hosts (MVP exception).

## 5. Pass/fail acceptance criteria

## 6. Database backup and restore

- MVP: `npm run db:backup` runs `pg_dump --format=custom` into `backups/` (gitignored); `npm run db:restore -- <file> [--into <dbname>]` creates the target database if needed and runs `pg_restore`; `--replace` restores in place after a typed confirmation. Backups contain hashed credentials only.
- The drill in T7 restores into a scratch database, compares row counts and recovers a deleted item; `docs/runbook.md` holds the steps.
- `data/import/<date>/` is a versioned baseline of the menus as imported.
- Item-level undo is the `revisions` table (T6).
- Supabase backups are decided at the move (T9).

## 9. Open questions

**Q1. Which free Vercel setup hosts the owner preview: a Pro trial team or the Hobby account?**
Vercel's fair-use page defines commercial use to include "Receiving payment to create, update, or host the site" and restricts Hobby teams to non-commercial use. A Pro trial is free for 14 days with no payment method, one per user account, and reverts to Hobby afterwards.
Assumption if unanswered: Kian starts a Pro trial team on the day the preview is first uploaded, so the 14 days cover the demo; the preview is revoked at the end.
Recommendation: the Pro trial. It is within Vercel's terms, costs nothing, and lifts the one-shareable-link limit as well.
Trade-off: a 14-day window and one trial per account; if the demo slips past 14 days the project must be re-uploaded under another account or the owner decides on a paid plan early.

**Q2. For Senso website-only items, may the import reuse an existing Mealsy section when the website heading differs only by case or a plural "s" (Appetizers / Appetizer, Salads / Salad, Senso Pizzas / Senso pizza)?**
Assumption if unanswered: yes, reuse; new sections only for Hot & Cold Beverages, Pancake & Waffle and Juice Bar.
Recommendation: reuse. Three near-duplicate sections named "Appetizers" and "Appetizer" would confuse the admin and the owner.
Trade-off: the rule is a small deviation from "under their website section names"; the report lists every placement so it can be reversed item by item.

No material problem was found with Next.js, Node.js and Postgres (local, then Supabase) for these requirements.
