# Roses menu showcase — project brief

Menu showcase and menu management system for the Roses venues in Richmond Hill, Ontario.
Kian is the owner and sole decision-maker; his PM reviews everything produced here.
This project is NOT part of Connex. No Connex code, data, contracts or infrastructure.

## Venues

- **Roses Kebab Land**: dine-in at 9218 Yonge St, take-out at 9108 Yonge St. One shared menu for both locations. Persian grill with a full bar.
- **Senso Café & Bites**: 9218 Yonge St. Persian breakfast, coffee, juices, ice cream, desserts, pizzas.

## Stack

Next.js (React, Node.js) with Postgres, built and run locally for the MVP: Next.js + Postgres in Docker (`docker compose up -d`, port 5433). No Vercel project, no deploys, no preview link and no Supabase until Kian decides on hosting.
PM build decision: no Vercel-only or Supabase-only features (no Vercel Blob, Vercel Cron, Edge Config, Supabase Auth or Storage). The app must run on any Node host with standard Postgres.
Public menu pages are pre-rendered at build time from the database, so they don't query it per visit; after hosting is decided they are regenerated when an admin saves.
The admin UI and its API live in the same Next.js project.
If you see a material problem with this stack for these requirements, raise it under Open questions with your recommendation. Do not switch stacks on your own.

## Rulings (Kian's decisions. Do not change them. If the plan needs one changed, raise it under Open questions.)

1. Display only: items, prices, descriptions, photos. No ordering, cart, payments, POS integration or cost management.
2. Base data is imported once from the sources below. After that, everything is editable in the admin and new items can be created. No live sync with Mealsy or any other system.
3. Built for Roses only. Not a multi-client product.
4. v1 venues: Roses Kebab Land (one menu, both locations) and Senso.
5. No umbrella landing page. Each venue has its own URL, its own on-brand page and its own logo loading animation.
6. English by default, with a Persian toggle (right-to-left).
7. Admin access is by PINs generated by the main admin. One simple admin UI manages all venues.
8. No approval workflow. Anyone with access can edit.
9. Hosting on Vercel. Final domain undecided.
10. Allergen, dietary and halal notes are optional per item and set only by the owner or an admin.
11. Item names and content are the venue's decision, including health-claim names. We flag problems; we never change content.
12. A prototype comes before the client proposal.

## Build decisions (the PM's. Challenge any of them in the plan, with reasons, if you disagree.)

- PINs are 6 digits. 5 failed attempts trigger a 15-minute lockout per venue. Each PIN belongs to one person and their venue(s), and can be revoked. The main admin signs in with email + password, not a PIN.
- The admin is designed for phones first and must be usable by staff with low tech skills.
- Every edit is kept in a history with one-click restore. This is an undo, not an approval step.
- The logo animation plays only while the menu loads and never adds delay. Kian, 2026-10-07: it plays on every page load and refresh, not only the first visit (replacing the PM's "skipped on repeat visits"); it is skipped only when the device has reduced motion turned on. Nothing about it is stored on the device. Kian, same day: the hand-over is smooth: the logo dissolves while the page slides in behind it (header, tabs, first heading, then the first rows one after another), CSS only, finished by about 2 s; the preview and reduced motion show the page at once.
- Public menu pages must reach Largest Contentful Paint ≤ 2.5 s in a Lighthouse mobile run.
- Missing Persian text falls back to English. Prices use Western digits in both languages. Persian text is drafted at import and editable in the admin.
- Allergen and dietary fields start empty. They are never filled from scraped data or by AI.
- When sources disagree on a price, Mealsy wins (it is what customers are charged). Every conflict is listed for the client; none are silently resolved.
- The import fixes spelling only. Factual errors are imported as-is and listed for the client.
- Vercel Pro plan at first deploy (the free Hobby plan does not allow commercial use). No QR codes are printed until the final domain exists.
- Simplicity over architecture: no registers, ID schemes or abstractions that the rulings don't require.

## Style tab rebuilt around colour tokens (Kian, 2026-10-08, built)

- Every colour the public pages use is a named token in `src/venues/tokens.ts` (the only public file allowed to hold colour literals; `scripts/check-colour-literals.mjs` lists any other and the suite requires 0), rendered as CSS variables in the page's own `<style>`. The customers' stylesheet is `src/styles/public.css` (Tailwind scoped to the public sources, language switch, intro, menu kit); the admin keeps `src/app/globals.css`.
- Groups follow the page as customers see it: Page, Header, Category tabs, Section headings, Item rows, Item popup (also the section list), Footer, Intro; every token has a plain-words label. The template's switches (logo animation, photos in the list, and what the header shows on the default template) are a separate Layout group below the colours, followed since 2026-10-08 by the layout of every section (List / Grid; see below); "featured items and cover photo" do not exist yet and are not in it.
- Linked colours: text, hairlines and chips derive from the background they sit on ("Auto") until set ("Custom", with "Back to auto"); changing a background updates its Auto tokens. A venue default pinned from the brand record (Senso's navy phone links; Kebab Land's logo tile, red labels and phone links; the default template's accent on the name, active tab, prices and phone links) gives way to Auto when the background under it changes and it would be unreadable. Day-one defaults are each venue's look of 2026-10-07; the six places that used pure black now use the kit's ink `#1d1d1f` (active tab text and underline, section-list button, popup title, popup price, close icon), listed in `reports/style-tokens/`.
- Readability guard on every save, in the tab and on the route: WCAG contrast 4.5:1 for text, 3:1 for large headings and the active tab underline; refused with one line (ratio, threshold, nearest colour that passes as a one-tap fix). Decorative hairlines, bands and placeholders are not guarded (they are a light shade of their background by construction).
- The preview and the controls point at each other: the open group's region is outlined in the preview (the Item popup group opens an item's sheet; the Intro group shows the overlay frozen), a tap on a region in the preview opens its group, and the colour under the picker shows live before it is saved. Every save: "Saved · Undo", preview within 1 s. Reset per group and "Reset all colours" (confirmed), both undoable. Style stays owner and admin only.
- Storage: `venues.style.colors` (already authorized); older `accent`/`tile` values are read as the venue's defaults and cleared by Reset all. No new dependency, no data-model change, public pages still without runtime JavaScript.

## Style tab: controls as the master, section layout List / Grid (Kian, 2026-10-08, built)

- Bug fixed: while a colour was being edited, the open group jumped to another group. Cause: the "open the group tapped in the preview" step ran again every time the tab's data reloaded after a save, so a group tapped earlier in the preview reopened over the one being edited. Now a preview tap is acted on exactly once, when it happens; a tap on the region of the group already open keeps the open colour; the outlined region is state owned by the editor and flows to both previews (laptop frame, phone overlay), so the preview always follows the controls and never the other way round. The suite's Style drill replays the scenario (preview tap, another group opened, a colour saved: the group and its colour stay open through the save and both reloads).
- Item popup and section list motion (Kian, 2026-10-08, later): the item popup slides up from the bottom edge when an item opens and slides back down before it closes (Close, a tap on the dim, Escape and Back all animate out); the photo is 4:3 with a short soft fade at its bottom edge (Kian, later the same day: much less shade than the first version, which covered 45 % of the photo), the title starting 12 px inside it; grid cards carry no description. The owner's allergen, dietary and halal notes (ruling 10) now show to customers in the popup under "Good to know" (chips for Halal / Not halal and the dietary words, "Contains …" for the allergens, the note in both languages), only when set; the public query carries `items.notes`. The section list opens and closes with the same motion, has a Close button on the language's start side (left in English, right in Persian), takes at most three quarters of the screen (the page and its tab bar stay visible behind it) and scrolls inside; a tap on a section starts its exit and the page's smooth scroll together. Reduced motion: no animation. CSS and the kit's inline script only; no runtime JavaScript, no new tokens.
- Section layout: every section is shown to customers as a **List** (the rows of 2026-10-07) or a **Grid** (two columns of cards with a big square photo, the name and the price, Uber Eats-style; the description shows only in the popup, Kian, same day), chosen per section in the Style tab's Layout group (owner and admin; staff get 403 on the field). Same colour tokens (Item rows), same item popup; an item without a photo keeps a placeholder so the columns stay even; the first two cards of the first section load their photo eagerly. Data-model change made for this: `sections.layout` text, 'list' | 'grid', default 'list' (migration 005), carried in the change records and by Undo. Alternative considered and rejected: a list of grid section ids inside `venues.style` (no migration, but the choice would not follow the section through delete, Undo and restore). Public pages still run without runtime JavaScript; no new dependency.

## Process rules for every Claude session in this repo (PM, 2026-10-08, after the step-2 review)

1. One working copy per session. A second session works in its own git worktree on its own branch (`git worktree add ../roses-<topic> -b <topic>`) and merges into `main` by rebase once its batch passes the suite. Never edit files in another session's working copy.
2. Evidence only from committed code. `npm run check` refuses to start when the working tree has uncommitted changes outside `reports/checks` (it prints `git status --short` and exits 2). Flow: commit the code, run the suite, commit the report. Every report.md names the exact commit it tested.
3. The run `reports/checks/2026-10-08T02-01-20Z` carries the line "Built with uncommitted changes from another session; not evidence for bcba8a8." The suite is run again on the commit the intro session makes.
4. Intro session: before committing, report exactly what changed in the intro's behaviour with measured timings (when it shows, how long, whether it repeats on reload). Kian is ruling on repeat plays; no change to repeat behaviour is merged until he has ruled.
